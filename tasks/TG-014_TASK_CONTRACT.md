## 7. Required behavior / invariants

**Общая boundary.** Все шесть mutations используют TG-012 kernel с обязательным `Idempotency-Key`, `APP_USER` principal effective actor, canonical fingerprint (включая байты multipart файлов), reservation/replay и атомарностью. TG-014 потребляет authoritative effective actor/context из TG-010 session и TG-011 current policy validation; в demo actor/context server-resolved по TG-013. TG-014 не разрешает demo actor самостоятельно, не создаёт второй session/auth mechanism и не кеширует права из token. Existing Case сериализуется Case row lock; TG-011 current authorization/tenant/resource/run visibility предшествует раскрывающим terminal/stale/state errors, также на replay. Только server-bound role/binding/access задают Resident, UK и contractor authority; client tenant/role/actor IDs и `allowed_actions` не являются authority. TG-009 `evaluateDomain` получает актуальный locked snapshot и server-derived inputs; его facts/projection/event plans применяются без второй машины переходов. Success — Interface §§10–15/32: `201` CreateCase, остальные `200`, `command_id/case_id/state/revision/created/event_ids`; response описывает committed effect, не полный sensitive snapshot.

**CreateCase.** Использовать authoritative effective Resident actor/context после TG-010 session resolution (в demo — с TG-013 server-resolved actor) и TG-011 current policy validation; в transaction заново проверить active AppUser/selected binding/ResidentPremisesAccess и authoritative принадлежность Organization→House→Premises/Category; organization/house/resident выводятся сервером. Из одного coherent locked set сохранить `category_name_snapshot`, `requires_access_snapshot`, `result_requirement_snapshot`, nullable `default_contractor_snapshot_id`, `house_address_snapshot`, `premises_label_snapshot`; последующие config изменения их не переписывают. Case и iteration создаются атомарно по Data Model §26.4 с non-null current iteration и deferred composite FK; optional initial Attachment/link rows входят в ту же transaction, без ложного EVT-009/Result. `NotificationIntent` на CreateCase не требуется.

**Resident CreateCase options/read.** `GET /api/v1/cases/create-options` по Interface §9A принимает только optional `premises_id`; auth — current Resident application session, effective tenant/actor/demo context выводятся сервером. На каждом запросе заново фильтровать current `ResidentPremisesAccess`, active Organization/House/Premises и active own-Organization categories, включая валидность non-null default dependency для нового Case. Вернуть лишь доступные `premises_id/house_address/premises_label` и для выбранного доступного помещения category `id/name/description/requires_premises_access/result_requirement`; ни admin config rows, ни default contractor/OrganizationContractor internals, ни arbitrary tenant selector. Отсутствующее/чужое/недоступное выбранное помещение — hidden `404`; non-Resident — `403`; malformed query — `400`. Без выбора помещения categories пусты. Ответ — current display options, не authorization/reservation/snapshot. Поздний `CreateCase` всегда повторяет все проверки в transaction; читатель не может создать Case по устаревшему options response. TG-014 экспортирует registerable route/plugin и handlers, TG-029 выполняет central registration.

В normal mode до Case/Iteration/initial attachments/EVT-001 требуется **единственный** mapped к Resident `MaxIdentity`: `LINKED_CONFIRMED`, non-null `delivery_chat_id/type`; отсутствие/неготовность → `409 MAX_DELIVERY_TARGET_NOT_READY`, ноль Case и остальных effects. Произвольный first/latest recipient запрещён. В demo synthetic Resident не использует normal mapping: recipient/readiness следует explicit `DemoRun.notification_recipient_max_identity_id` и TG-013 demo contract. Session/current ACTIVE run принадлежит real identity; совместимый TG-013 currentness lock/revalidation и primary binding в той же transaction фиксируют immutable `Case.demo_run_id` и `DemoRun.primary_case_id` только из NULL. Different-key второй primary → `409 DEMO_PRIMARY_CASE_EXISTS` без второго Case; archive/start race не позволяет bind archived/foreign run. Same-key retry следует protected replay TG-012.

**selected != sent != accepted / privacy.** Selected-only contractor не получает LIVE list/read/act/download. Current sent/pending target имеет только acceptance context Product Spec §2.4: Case ID, адрес/помещение, категория, описание, initial attachments, простое result requirement и необходимая поручению история/коммуникация; действия только accept/reject. Рабочие права возникают после accepted current Assignment. Reject сохраняет **тот же Case, тот же iteration ID/no и историю**, немедленно снимает current authority; старые Selection/Assignment остаются historical. UK видит точную reason; Resident responses/snapshot/activity её не содержат и показывают «УК уточняет исполнителя»; contractor не получает чужие причины/административные события. Результат собственного reject может отражать введённую reason по canonical contract, но не создаёт дальнейший LIVE или replay доступ после отзыва authority.

**REWORK A→B.** Входной fixture уже содержит N+1, созданную TG-016 `ReturnToRework`; accepted Assignment A из N может оставаться current до смены исполнителя. Select B по current N+1 (B != current executor A) сохраняет `REWORK`, создаёт Selection B, атомарно очищает current assignment/executor A. A сразу теряет list/read/activity/act/attachment/download LIVE access, включая protected replay; accepted Assignment A/history неизменны. B selected-only доступа не имеет. Send B по exact Selection B переводит в `SENT_TO_CONTRACTOR`, B pending получает limited context; только accept B даёт `EXECUTION`/executor B. **Case и N+1 ID/no неизменны на select/send/accept/reject**, EVT-013/014 повторно не создаются. Если B откажется, действует обычный TR-006: `ACCEPTED_BY_UK` в той же N+1, затем новый select/send/accept. Same-contractor rework без переназначения не требует нового acceptance и не расширяет этот slice.

**Locks / config revalidation.** Для используемых rows строго соблюдать Architecture §9.4 / Data Model §29.4 / TG-012: principal/key reservation → Case (если существует) → Organization → House → Premises → Category → Contractor → OrganizationContractor → actor/access/binding rows по stable PK → child writes. CreateCase удерживает relevant Organization/House/Premises/Category, при необходимости snapshot default Contractor/OrganizationContractor, access/binding rows до commit; snapshot читается только из этого set. Select/Send под Case lock дополнительно lock/revalidate exact Contractor и active OrganizationContractor; Send проверяет доступность заново, даже если Select ранее прошёл. Commands используют `FOR SHARE`/эквивалент, совместимый с общим протоколом config writer `FOR UPDATE` в том же порядке; нескольким rows одной сущности — stable PK. TG-013 bounded DemoRun/currentness locks сохраняют совместимость с concurrent Start/bind, не заменяя config protocol. TG-014 локально доказывает собственный lock order и revalidation по current active/inactive config fixtures, включая command-first состояние, без ожидания production TG-018 writer. Если deactivation уже committed, command перечитывает inactive config и откатывается без effects. Полную гонку обеих production сторон и оба commit orders доказывает TG-026. Category deactivation запрещает новые Cases, но не переписывает existing Case snapshot и не требует переоценки его старой category для Select/Send. Никаких unlocked active-check, process mutex/retry workaround или mixed config versions.

**Conflicts / ledger.** Different-key команды после lock перечитывают committed context: AcceptCase loser → `409 INVALID_STATE`; old iteration → `409 STALE_ITERATION`; send old selection → `409 STALE_SELECTION`; accept/reject old Assignment → `409 STALE_ASSIGNMENT` либо `INVALID_STATE` при изменившемся state. Exact старый Assignment не становится valid даже при новом назначении той же организации. Concurrent selections могут последовательно быть valid, только пока current state разрешает выбор; отправка старого Selection всё равно запрещена. Accept||reject — first-valid-wins, ровно одна decision/event; loser не меняет facts. **Эти 409 только после current visibility gate**: утративший доступ после rejection/reassignment получает hidden `404`, не revealing stale detail. Visible forbidden action → `403`; empty reason → `422 REJECT_REASON_REQUIRED`, inactive create category → `422 CATEGORY_INACTIVE`, contractor availability/input — canonical codes/HTTP по Interface §§4/31. Нет retarget/no-op вне approved contract; replay не повторяет уже совершённый business transition. TG-012 атомарно фиксирует facts, projection/`updated_at`, append-only EVT-001…006 с корректными targets/actor/iteration/sequence, post-command revision и stored success; failure оставляет ноль effects/reservation. Generic event fallback и дополнительные события для этих шести команд запрещены.

## 9. Acceptance criteria

Шесть lifecycle commands сохраняют таблицу §7 и exact canonical HTTP/events/projections; отдельный read endpoint реализует только Interface §9A. Options не выдаёт admin/foreign/internal data и ограничен текущим доступом Resident; смена конфигурации/доступа между options read и command не обходит transaction revalidation. CreateCase имеет readiness rollback, coherent immutable snapshots, initial iteration/revision 1 и atomic demo primary bind. selected/sent не создают executor; rejection очищает три current pointers, сохраняет identity/iteration/history и privacy. Initial rejection A→B и отдельный REWORK A→B проходят; N+1 не растёт повторно, A отозван сразу, B становится executor только после accept. Current authorization/replay, TG-012 serialization/rollback, собственный lock order и config revalidation доказаны локально; production cross-module config races с TG-018 относятся к TG-026. Registerable boundary передаётся TG-029 без изменения central registry TG-014.
