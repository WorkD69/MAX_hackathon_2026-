## 7. Required behavior / invariants

**MAX boundary.** `MaxAdapter` предоставляет typed операции `sendMessage(validatedChatId, message/openAppAction)`, `listSubscriptions()`, `createSubscription(expected)`, а также разбор известного `Update` после проверки webhook secret; real implementation изолирует HTTP/MAX response schemas, fake implementation доступен только test composition. Все реальные вызовы идут на `https://platform-api2.max.ru` с `Authorization: <MAX_BOT_TOKEN>` и ограниченным `MAX_REQUEST_TIMEOUT_MS`. `POST /messages?chat_id=<snapshot delivery_chat_id>` использует JSON body (`text`, при кнопке `attachments:[{type:'inline_keyboard',payload:{buttons:[[{type:'open_app',text:'Открыть приложение'}]]}}]`), `notify` не ставится в `false`; не адресовать `user_id` по догадке. При каждом валидном `bot_started` bot отправляет приветствие с этой `open_app` кнопкой в документированный `chat_id` события; кроме этого TG-032 настраивает штатное действие открытия Mini App в профиле бота. Оба пути ведут к Mini App, настроенному на публичный `PUBLIC_APP_URL`; официальный wire `web_app` обозначает бота/ссылку на бота, поэтому не подставлять туда URL приложения без отдельного подтверждения официального contract. Контекстный `startapp` не является identity/authorization или обязательной корреляцией.

**Webhook.** `POST /integrations/max/webhook`: перед body parsing, business обработкой и исходящими вызовами проверять точное значение `X-Max-Bot-Api-Secret` относительно typed `MAX_WEBHOOK_SECRET` безопасным сравнением; отсутствующий/неверный секрет отклонять без side effects и без secret в ответе/логах. После успешной проверки принимать только документированный `Update`, неизвестный тип не превращать в product command. Вернуть HTTP 200 без обязательного JSON до 30 секунд, не ожидая Bot API/длинной transaction. Валидный `bot_started` запускает после acknowledgement bounded async отправку обязательного приветствия с `open_app`; сбой отправки фиксируется безопасной диагностикой и не задерживает 200. Повторный `bot_started` может повторить приветствие; этот non-business greeting не создаёт `NotificationIntent`. Штатное действие профиля бота из предыдущего абзаца обеспечивает вход в Mini App при сбое приветствия. Публичный endpoint в TG-032: HTTPS/443, корректные hostname/certificate/full chain.

**Subscription.** По `MAX_SUBSCRIPTION_RECONCILE_INTERVAL_MS` и при старте live процесса сравнивать `GET /subscriptions` с ожидаемым exact HTTPS webhook URL и нужными `update_types` (`bot_started`, `message_created`). Отсутствующую подписку создавать `POST /subscriptions` с `url`, `update_types`, `secret`; `200` с `success:false` считать ошибкой, а не успешной reconciliation. `GET` не доказывает действующий secret; защиту подтверждает отдельный webhook smoke в TG-032, не предположение о сохранённом значении. Ошибки логировать без token/secret, повторять на следующем цикле; не удалять чужие подписки. MAX может удалить подписку после длительной недоступности, поэтому повторный reconcile обязателен. Секрет должен удовлетворять официальному `^[a-zA-Z0-9_-]{5,256}$`; несоответствие typed TG-003 описано в §12.

**Outbox.** Consume only existing `RESULT_READY` intent со snapshot `recipient_max_identity_id`, `delivery_chat_id/type` из TG-007/TG-015; не переизбирать recipient по текущему состоянию MaxIdentity. Poll/concurrency/lease/retry/max attempts берутся только из typed TG-003 (`NOTIFICATION_WORKER_POLL_INTERVAL_MS`, `NOTIFICATION_WORKER_CONCURRENCY`, `NOTIFICATION_LEASE_MS`, `NOTIFICATION_RETRY_BASE_MS`, `NOTIFICATION_RETRY_MAX_MS`, `NOTIFICATION_MAX_ATTEMPTS`). Короткая PostgreSQL transaction с `FOR UPDATE SKIP LOCKED` атомарно берёт due `PENDING|RETRY` либо expired `CLAIMED`, ставит `CLAIMED`, новый random UUID `claim_token`, `claimed_at`, `lease_expires_at`, увеличивает `attempt_count`, ставит `last_attempt_at=claimed_at`, commit. Только после commit real adapter делает network call. Отдельный finalize меняет строку лишь при `status=CLAIMED AND claim_token=<current token>`; устаревший token не может переписать новый claim. После успеха `DELIVERED`, `delivered_at`, optional `provider_message_id`, claim clear; при временной ошибке `RETRY`, `next_attempt_at`, claim clear; при постоянной/исчерпанном лимите `PERMANENT_FAILURE`, `next_attempt_at=NULL`, claim clear. Поля в каждом статусе соблюдают Data Model §19; `attempt_count` считает зарезервированные claim/send попытки **текущего цикла**, включая crash после claim до сети; `last_attempt_at` — время последней reservation, сохраняется при redrive. Expired lease reclaim не держит network под lock. External delivery at-least-once: crash после send до finalize может повторить внешнее сообщение, но DB business facts остаются единственными.

**Failure policy.** Timeout/network, HTTP 408/429 и 5xx → transient `RETRY` с bounded exponential backoff `min(RETRY_MAX, RETRY_BASE × 2^(attempt_count−1))`, без unbounded retry и без новых business rows; когда `attempt_count` достигает `NOTIFICATION_MAX_ATTEMPTS`, terminal `PERMANENT_FAILURE` с безопасным кодом `ATTEMPTS_EXHAUSTED`. HTTP 401 (Bot Token) и **все остальные** 4xx → `PERMANENT_FAILURE` с sanitized auth/request/target code, без автоматического переписывания payload или выбора другого адресата. Любой 3xx → permanent protocol/config failure: redirect не follow, чтобы не отправить Authorization другому host. Валидный documented `200` с ожидаемым message body → success; иной 2xx, malformed/non-JSON `200` или иная неоднозначная transport response → transient, поскольку MAX мог отправить сообщение. Если последний `CLAIMED` истёк после crash при исчерпанном лимите, короткое DB recovery завершает **тот же** intent как `PERMANENT_FAILURE` с compare-and-set по текущему claim token, без дополнительного send; успешный поздний finalize старого токена после нового claim невозможен. `Result`/EVT-008/Case state committed и не откатываются из-за доставки.

**Redrive.** Team-only CLI принимает существующий `notification_intent_id` и явный operator context, без публичного API; после исправления token/config атомарно переводит только `PERMANENT_FAILURE → RETRY` той же строки, увеличивает `operational_redrive_count`, сбрасывает `attempt_count=0` для нового ограниченного цикла, очищает error/claim, задаёт `next_attempt_at`, пишет structured audit log с прежним числом попыток без secret. `last_attempt_at` остаётся временем последней claim reservation прошлого цикла до следующего claim. Это даёт не больше `NOTIFICATION_MAX_ATTEMPTS` reservations после **каждого** ручного redrive и не обходит лимит автоматическим retry. Delivered/pending/claimed/redriven не клонировать. Dedupe TG-007 `UNIQUE(dedupe_key)` и `UNIQUE(result_id,notification_kind)` сохраняется; redrive не меняет эти поля.

## 12. Blocker protocol

**BLOCKER TG-003/MAX:** TG-003 typed `MAX_WEBHOOK_SECRET` допускает любые UTF-8 32–4096 bytes, тогда как официальный `POST /subscriptions` допускает только `^[a-zA-Z0-9_-]{5,256}$`. Например, валидный для TG-003 Unicode или 257-символьный secret MAX отклонит. До upstream typed validation fix и contract review нельзя объявлять live subscription готовой, добавлять ad hoc env validator в TG-019 или выдумывать другой webhook protocol. Если official MAX docs/approved architecture конфликтуют в wire-семантике `open_app`, delivery target или webhook, остановить затронутую implementation и сообщить конкретный `SPEC/ARCHITECTURE CONFLICT` владельцу canonical decision. Точно так же остановиться при неверном implementation `BASE_SHA`, неполном TG-007, несовместимой DB форме или выходе за write scope. Contract authoring и independent review допустимы; implementation blocked until TG-007 complete **и** blocker TG-003 закрыт.
