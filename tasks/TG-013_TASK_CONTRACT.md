## 7. Required behavior / invariants

- **Start DemoRun.** `POST /api/v1/demo/runs` принимает только canonical `{scenario_key:"primary-housing-demo"}` и обязательный `Idempotency-Key`. Principal — validated real `MAX_IDENTITY`, даже если effective actor отсутствует. При `DEMO_MODE=false` — `403 DEMO_MODE_DISABLED`; если exact real identity не имеет confirmed usable outbound `delivery_chat_id/type`, fail-closed до создания/архивации run по canonical error contract. В одной transaction по TG-012: reservation/replay, serialization по real MaxIdentity, archive только `status/archived_at` прежнего ACTIVE run, создание нового ACTIVE run с explicit notification recipient этой real identity и пяти `DemoRunActor` из TG-008 allowlist. Ответ `201` содержит new `demo_run_id`, `ACTIVE`, `primary_case_id:null` и ровно `RESIDENT`, `UK_EMPLOYEE`, `UK_ADMIN`, `CONTRACTOR_EMPLOYEE`; token в нём нет. После первого Start и после repeat клиент выполняет fresh signed MAX bootstrap, получает token с новым current run, затем переключается на `RESIDENT` и вызывает `CreateCase`. Старый token не используется для switch/Case. Same-key retry replay'ит `201` только пока сохранённый run остаётся current и пройден current-run security gate TG-012; после архивации сохранённого run protected replay отказывает по canonical visibility/session semantics, не возвращая ID archived run. Новый key создаёт новый run. Partial unique по identity и currentness revalidation удерживают максимум один ACTIVE run.
- **Repeat и primary bind.** Старт не создаёт Case. Resident затем вызывает обычный `CreateCase`: TG-014/TG-012 в одной transaction фиксируют immutable `Case.demo_run_id=current ACTIVE run` и `DemoRun.primary_case_id` только если NULL. Второй different-key primary Case в том же run получает `409 DEMO_PRIMARY_CASE_EXISTS` без второго Case/effects; same-key retry следует replay. Новый run получает новый Case ID; прежние Case, run-to-Case references, snapshots, events, results, attachments и history сохраняются. Archived/foreign run или Case скрыт/отклонён до раскрывающих stale/state ошибок; все protected reads, mutation и replay проверяют owner/current run и TG-011 authority.
- **Session/policy integration (TG013-CRIT-001).** Server-resolved DEMO context однозначно связывает real MAX identity, current owned ACTIVE run, конкретный allowlisted effective AppUser и выбранный authoritative RoleBinding/context (role, organization/contractor scope); клиент его не задаёт. TG-010 session seam обязан сохранять эту однозначную server-bound связь и передавать её TG-011 для current policy validation. Existing demo token с `role_binding_id=null` и lookup только DemoRunActor/AppUser недостаточны для доказательства прав: выдача/восстановление действующего actor требует разрешения exact selected binding/context через согласованный seam, без union/fallback на другой binding. Представление context в signed application session и совместимость token остаются ответственностью TG-010; TG-013 не вводит новый token/auth protocol. Bootstrap, `GET /api/v1/session`, switch и каждый protected request используют TG-011 current policy: заново проверяют AppUser/selected RoleBinding active, organization/contractor scope, required current access (ResidentPremisesAccess/UKHouseAccess и другие relevant rows по policy), owner/current DemoRun/allowlist и, где применимо, current Assignment/executor authority. Криптографически действующий Bearer **не замораживает rights до expiry**. Revoke/deactivation binding/access или invalid/inactive actor действует на следующий protected session/bootstrap request; старый actor не сериализуется как действующий. Mutation/replay сохраняют TG-011/TG-012 transaction/security ordering. Предписанный seeded pre-assignment contractor entry без Case access остаётся допустимым по current policy, а не обходом revalidation.
- **Restore.** TG-010 bootstrap по fresh signed MAX context и `GET /api/v1/session` re-resolve единственный ACTIVE run по real identity и возвращают authoritative `demo_run_id`, nullable `primary_case_id`, real identity и effective actor/context **только после current policy revalidation через seam выше**. Reload и fresh bootstrap в mobile/web продолжают тот же run/Case; normal bootstrap не создаёт run. Если previous effective actor более не valid/authorized, restore его действующих полномочий denied по canonical error/session semantics; не возвращать его как valid actor и не выбирать fallback actor/binding. Fresh bootstrap может вернуть `effective_actor=null` и потребовать явного role switch по Interface §2.3; это не восстановление revoked actor. Клиент не восстанавливает права из сохранённой роли/alias. Token старого run после archive не даёт доступ к старому Case.
- **Actor switch.** `POST /api/v1/demo/session/actor` с обязательным `Idempotency-Key` принимает strict `{role_view:<одна из четырёх ролей>}`. Idempotency principal — **real `MAX_IDENTITY`**, одинаковый до выбора actor и для разных role tokens этой identity; `APP_USER` не разделяет switch keys. Сервер проверяет `DEMO_MODE`, real session, owner/current ACTIVE run, `DemoRunActor` allowlist, active AppUser/RoleBinding и relevant access; Resident/UK views выбирают соответствующего предсозданного actor. Для Contractor view по current `primary_case_id`: current pending Assignment contractor, иначе current executor contractor, иначе TG-008 deterministic default только для pre-assignment entry, без Case access. A/B — два concrete actor одной роли; response `200` — новый signed token и authoritative session context. Protected replay проходит current-run/actor/binding gate TG-012; после смены current run не возвращает старый token. Роли и права не суммируются; текущая видимость Case определяется по выбранному actor и current run.
- **Races.** Concurrent starts одной identity сериализуются по MaxIdentity и TG-012 principal/key: same key подчиняется current-run protected replay gate, разные keys последовательно создают runs и оставляют один ACTIVE; каждый committed старый Case неизменен. Start против `CreateCase`/switch/restore проверяется под совместимым current-run lock/revalidation: ответ не выдаёт полномочия на archived run; уже выданный stale token отклоняется при следующем protected request. Два switch для одного ACTIVE run могут вернуть отдельные токены выбранных views; каждый токен содержит один actor и при использовании заново проверяется against current run/bindings, без глобального client-selected actor или union rights. Restore не смешивает `primary_case_id` одного run с ID другого.

Switch принимает только `role_view`; server-resolved candidate до выдачи token/authoritative response проходит current binding/access validation TG-011 через TG-010 seam. Если candidate inactive/invalid, binding revoked или required access больше не current-authorized — **switch denied** по canonical error/session semantics, без token с правами этого actor и без подмены candidate клиентским ID или fallback actor. Successful switch/replay не обходит текущую policy.

## 9. Acceptance criteria

На real PostgreSQL один validated MAX identity управляет максимум одним ACTIVE DemoRun. Start и повтор создают отдельные runs; новый run начинается с `primary_case_id=null`, первый `CreateCase` связывает свой Case, второй не создаёт Case. Старый Case/history остаётся без изменений и недоступен для mutation из нового run. Bootstrap/session восстанавливают текущие run/Case в mobile и web; switch принимает только role view, server выбирает A/B и выдаёт права одного actor. Disabled demo, foreign/archived scope и not-outbound-ready identity fail closed согласно canonical error/visibility order.

TG-010/TG-011 seam §8 интегрирован владельцами: после revoke/deactivation binding/access или invalid/inactive actor следующий `GET /api/v1/session` при still-valid Bearer и fresh signed MAX bootstrap не восстанавливают старого actor как authorized; switch не выдаёт права invalid candidate. Valid actor restore сохраняется. Session/token ownership TG-010 и policy ownership TG-011 неизменны, второго auth/session framework нет.

Targeted API + real-PostgreSQL integration suite: точные четыре views/пять allowlisted actors; Start response без token/Case, затем fresh bootstrap → Resident switch → `CreateCase` для первого и повторного запуска; repeat `Run #1/Case A → Run #2/Case B` с неизменными A/history; concurrent same-key/different-key starts и один ACTIVE; same-key Start replay при current run и отказ protected replay после его архивации без утечки старого `201`; atomic first primary bind, second-key `DEMO_PRIMARY_CASE_EXISTS`, rollback без orphan Case/bind; reload, mobile/web fresh bootstrap и `GET /session` с тем же current run/Case и без auto-create; switch strict `role_view` only, Resident/UK и pending Assignment A→B/current executor/default contractor resolution; same-key switch из разных действующих role tokens одной real identity использует один `MAX_IDENTITY` principal и current security gate; request с forged alias/IDs/contractor или пятой ролью отвергнут; права A/B и ролей не union'ятся. Проверить `DEMO_MODE=false` `403`, foreign/archived run/Case hidden/denied, not-outbound-ready Start без mutation, stale token после нового run, switch/start/restore races и непротиворечивый context. После implementation выполнить targeted suite, `npm run typecheck`, `npm run build`, `npm test`, `git diff --check` и сообщить результаты.

Targeted seam requirements для TG013-CRIT-001 (через реальные TG-010 session/bootstrap consumers и TG-011 policy, не resolver-only fixtures):

- **A — binding revoke:** existing demo session с selected actor, current run и криптографически действующим unexpired Bearer; revoke/deactivate exact RoleBinding; следующий `GET /api/v1/session` не восстанавливает actor как valid/authorized, canonical denial без fallback binding/actor. Fresh signed bootstrap после revoke также не возвращает прежнего actor как действующего; canonical actor-null bootstrap допустим.
- **B — access/actor revoke:** те же условия; отдельно revoke/deactivate required ResidentPremisesAccess/UKHouseAccess и другие relevant access rows по TG-011 policy, отдельно invalid/inactive AppUser/allowlist actor. Следующий session read/bootstrap не выдаёт stale effective rights несмотря на valid token.
- **C — switch after revoke:** client sends только `role_view`, server candidate утратил selected binding/required access либо inactive; switch denied без нового authorized token/context. Same-key protected switch replay после revoke также не возвращает прежние права.
- **D — valid actor:** unchanged active binding/access/policy; session restore успешен с тем же authoritative actor/run/primary Case; fresh bootstrap сохраняет run/Case и соблюдает canonical explicit-switch/actor-null semantics, без auto-create.
- **E — no client authority:** forged actor/binding/org/contractor IDs или alias не выбирают effective context; role_view-only candidate и exact selected binding выводятся сервером; неоднозначный selected binding fail closed по TG-011, несколько bindings не дают union/fallback rights.
