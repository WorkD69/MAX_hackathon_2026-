## 7. Required behavior / invariants

- **Principal и fingerprint.** Authenticate signed application session и server-selected effective context; `APP_USER` с exact effective `app_user_id` — Case/config business commands, `MAX_IDENTITY` с real validated `max_identity_id` — допустимые до effective actor demo technical commands. Ровно один из двух IDs, без fake/system AppUser. Обязательный `Idempotency-Key`; после schema validation canonical fingerprint охватывает method, canonical path, command type и normalized payload. Для multipart он также охватывает ordered logical file descriptors/значимую metadata и SHA-256 **байтов каждого файла** в стабильном logical order; случайные boundary и порядок transport headers не влияют. Изменение normalized body или file bytes при том же principal/key даёт `409 IDEMPOTENCY_KEY_REUSE` после применимого security gate.
- **Единственная reservation.** В одной DB transaction до lifecycle/stale validation создать `CommandExecution(IN_PROGRESS)` для discriminated `(principal,key)`. TG-007 partial unique indexes дают одного owner; concurrent same-key contender ждёт исхода owner transaction и перечитывает persisted row. При том же fingerprint и `SUCCEEDED` возвращается сохранённый canonical HTTP status/body без повторных business writes, событий и revision increment; при другом fingerprint — key-reuse conflict. При rollback owner reservation исчезает, следующий retry может стать owner. Никакого committed `IN_PROGRESS` как успешного эффекта и никакого orphan `SUCCEEDED` без committed command effects.
- **Authorization перед protected replay.** Reservation/duplicate lookup может предшествовать Case lock, но duplicate decision не выдаёт protected status/body, key-reuse detail или наличие stored success наружу до текущего TG-011 security gate. Для existing Case kernel берёт authoritative Case lock; если requested и stored resource у duplicate различаются, оба Case row locks берутся в стабильном ascending `case_id` order после reservation, до обоих security decisions. Для **любого duplicate**, включая CreateCase и non-Case command, проверить current TG-011 visibility/authorization **запрошенного и сохранённого** resource/context при их различии до replay либо key-reuse ответа; любой hidden resource даёт canonical `404`, видимый forbidden action — `403`. CreateCase duplicate включает created Case из persisted canonical response и requested house/premises/run context: после Case lock все relevant requested/stored config/access rows берутся по global entity order и stable PK; поэтому изменённый House с hidden scope не раскрывает прежний success через `IDEMPOTENCY_KEY_REUSE`. Non-Case duplicate аналогично проверяет оба current resource/run/config contexts под совместимыми locks в canonical resource/PK order. Revalidate active selected binding/access, current tenant/resource/DemoRun visibility и relevant current Assignment/executor по TG-011; revoked binding/access и old contractor после reassignment не получают прежний protected response по старому key. Неизменный уполномоченный principal получает legitimate replay без повторной terminal/exact-target/state validation уже выполненной команды. TG-011 определяет policy decision, TG-012 реализует reservation, gate placement и replay.
- **Approved order для нового existing-Case command.** Authenticate → derive principal → schema/fingerprint → `BEGIN` → acquire/wait `CommandExecution` reservation → `SELECT Case ... FOR UPDATE` → re-resolve current TG-011 authority → tenant/resource/run visibility (`404` до revealing errors; видимый, но forbidden action — `403`) → terminal guard → exact target IDs/currentness → current state/iteration/pointers → lock/revalidate dependent mutable configuration в canonical order → domain/input validation → domain writes → current projection и `Case.updated_at` → append `CaseEvent(s)` → required `NotificationIntent` → post-command `Case.revision` → finalize ту же execution row `IN_PROGRESS → SUCCEEDED` с canonical status/body и этим revision → `COMMIT`. Command-specific `Transaction effect` задаёт atomic effect set, не переопределяет этот физический порядок, кроме явно указанной FK/deferred-FK необходимости внутри той же transaction.
- **Locks и stale.** Global order: principal/key reservation → Case row, если есть (для duplicate с двумя разными Cases оба по ascending `case_id`) → Organization → House → Premises → Category → Contractor → OrganizationContractor → actor/access/binding rows по stable PK → child writes. Config writers берут совместимые конфликтующие locks; CreateCase, SelectContractor и SendAssignment перечитывают relevant active config под ними. Разные keys одного Case сериализуются по Case lock; второй читает committed current context. Exact Selection/Assignment/Result/Feedback/iteration identities не заменяются новыми target; loser получает semantic `409` (`STALE_SELECTION`, `STALE_ASSIGNMENT`, `STALE_RESULT`, `STALE_ITERATION`, `INVALID_STATE` и другие command-specific codes) либо явно разрешённый canonical replay/no-op. First valid wins. `revision` — metadata для freshness; не CAS gate.
- **CreateCase / non-Case.** CreateCase reserve-first, затем current actor/access и coherent config locks до snapshot/Case writes; Case row lock до создания невозможен. Соблюдать deferred Case/Iteration bootstrap, readiness gate и DemoRun binding из Architecture §9.4 / Data Model §28.2. Первая committed revision и canonical response — `1`. Non-Case config/demo commands используют тот же principal/key/replay/rollback protocol и утверждённые resource/run/config locks вместо несуществующего Case lock.
- **Atomicity.** Ошибка до commit откатывает reservation, business writes, current projection, events, outbox intent и successful response вместе; повтор с тем же key после rollback обрабатывается как новый owner. Успешный ответ сохраняется до commit только после всех эффектов с post-command revision. После commit retry возвращает ровно stored status/body; network failure после commit не разрешает второй business fact.

## 9. Acceptance criteria

Один runner обслуживает все mutating command categories и сохраняет один successful canonical result на `(principal,key)`; same-key duplicate ждёт и replay'ит, changed payload/file bytes конфликтует. Current authorization защищает replay и все revealing stale/terminal errors. Different-key Case commands сериализуются, exact-target loser не меняет Case и получает предусмотренный semantic conflict/no-op. Любая failed transaction оставляет ноль business effects и reservation; success хранит post-command revision, включая CreateCase `1`.

## 10. Required tests

- Controlled real-PostgreSQL concurrent same-key requests: один owner, waiter, один committed effect/`SUCCEEDED`, exact canonical stored status/body; same key + same payload replay без новых writes/events/revision; same key + changed JSON payload и changed multipart file bytes (при прежней metadata) → `IDEMPOTENCY_KEY_REUSE`; boundary/header variation при тех же logical bytes не меняет fingerprint. Changed-resource key reuse с двумя Cases в обеих направленностях A→B/B→A доказывает stable lock order, отсутствие deadlock и оба visibility gates до ответа; CreateCase House A success → duplicate с hidden House B и non-Case requested/stored context mismatch дают hidden `404` до key-reuse detail.
- Two different keys same Case: Case-lock serialization и first-valid-wins; exact old Selection/Assignment/Result/iteration conflicts mapped к semantic `409`, без silent retarget; явно разрешённый no-op/replay только по command contract; revision сам по себе не влияет на acceptance.
- Visibility-before-stale/terminal: foreign tenant/run/hidden resource получает `404` даже со stale target или stored success; видимое запрещённое action получает `403`. Same-key replay при revoked binding/access и после contractor reassignment denied без stored response; при unchanged current authority replay allowed, хотя исходная business transition уже не current.
- Rollback на validation/error/DB failure удаляет reservation, domain writes, projection, event и intent; retry с тем же key успешно резервирует заново. Ни одного orphan successful `CommandExecution`; committed success содержит canonical post-command revision, CreateCase — `1`. Проверить config deactivation race и required lock order вместе с TG-007/TG-011 fixtures. На implementation stage запустить targeted tests, `npm run typecheck`, `npm test` и показать результаты.
