## 2. Goal

Зафиксировать минимальный approved configuration API своей УК: reads, Organization update, House/Category create/update, result requirement/default contractor, contractor directory/binding и привязки предсозданных пользователей. ### Authorization и mapping

**Success wire.** Девять writes возвращают strict TG-002 named aliases по Interface §24.1: `OrganizationPatchSuccessSchema` (`200`), `HouseCreateSuccessSchema` (`201`), `HousePatchSuccessSchema` (`200`), `CategoryCreateSuccessSchema` (`201`), `CategoryPatchSuccessSchema` (`200`), `ContractorCreateSuccessSchema` (`201`), `ContractorBindingPutSuccessSchema` (`200`), `UserRoleBindingPutSuccessSchema` (`200`), `ContractorEmployeePutSuccessSchema` (`200`). Alias использует существующую own-scope read projection соответствующей сущности; contractor включает own OrganizationContractor, user — только разрешённые bindings/access. Нет `command_id` envelope, audit payload или публичного `config_revision`. Same-key authorized replay возвращает точно сохранённые исходные status/body; успешный ответ отражает committed эффект после всех связанных изменений.

Reads и mutations — только active `UK_ADMIN` с server-selected effective context; никаких объединений прав всех bindings и доверия роли из payload. Organization определяется из текущей TG-011 policy. На reads права перечитываются до projection, на mutation — внутри transaction под совместимыми locks. Valid session не сохраняет отозванные права; demo obeys current run/actor boundary TG-011.

Foreign/absent/hidden target или linked target — canonical hidden `404` до revealing validation/replay detail; видимый own resource с forbidden action/non-admin — `403`; видимое invalid same-org mapping/inactive dependency — `422`, idempotency key conflict — `409` по canonical errors. Unknown user/House/Contractor IDs не становятся разрешёнными из-за их наличия в request. Bind existing Contractor разрешён только для directory target, доступного policy; доступность для binding не даёт LIVE Case rights. Связи ContractorEmployee не дают прав на чужую УК и не редактируют чужую конфигурацию; global Contractor/предсозданный user не считаются exclusively owned текущей УК. Не изобретать tenant column для contractor role: Data Model требует contractor_id и NULL organization_id; границу устанавливает TG-011.

Ровно четыре роли: `RESIDENT`, `UK_EMPLOYEE`, `UK_ADMIN`, `CONTRACTOR_EMPLOYEE`, с shape Data Model §6.2. Resident binding не выдаёт произвольный ResidentPremisesAccess; использовать только preconfigured scenario access. Только `ResultRequirement = NONE | PHOTO | FILE`; текст результата всегда обязателен, NONE отменяет лишь дополнительные материалы. `default_contractor_id=null` снимает default; non-null требует active Contractor и active OrganizationContractor той же УК, перечитанные под locks.

### Доступный предсозданный AppUser (F1)

Для server-selected Organization `O` пользователь `U` доступен для configuration role assignment тогда и только тогда, когда AppUser уже существует и есть хотя бы одно authoritative own-scope основание: UK binding к `O` (включая inactive); preconfigured ResidentPremisesAccess или UKHouseAccess к помещению/дому `O`; CONTRACTOR_EMPLOYEE binding к Contractor с own OrganizationContractor; либо явная server-owned eligibility этого предсозданного test-user для `O` в доверенном seed/scenario наборе. Последнее основание задаётся преднастройкой сценария с reproducible aliases/business keys (Data Model §36), независимо от наличия RoleBinding; это не новый endpoint, tenant column AppUser или AppUser lifecycle. В demo дополнительно соблюдается allowlisted actor/current run boundary TG-011. `is_synthetic=true`, знание UUID, отсутствие bindings и payload клиента сами по себе eligibility **не дают**. Inactive основания позволяют управлять доступной конфигурацией, но не дают LIVE rights; AppUser.active не изменяется этими endpoints.

**Да: own/synthetic eligible AppUser без текущего own-org RoleBinding появляется в `GET /api/v1/config/users` и доступен для первого PUT.** Если нет own bindings/access, соответствующие массивы ответа пусты. GET и оба user-binding PUT используют один предикат доступности; для отсутствующего или не eligible пользователя — hidden `404` до revealing validation/replay. Eligibility повторно проверяется внутри mutation transaction, а не выводится из будущей запрашиваемой роли. Не выдавать foreign-only users, включая чужих synthetic users. При собственной eligibility глобального/shared AppUser проецировать только его разрешённые own-scope bindings и UKHouseAccess к домам `O`; чужие tenant bindings/access и факт чужой принадлежности не раскрываются. Resident binding допустим только с own preconfigured scenario access; contractor binding — только в разрешённом contractor scope, без выдачи прав на другую УК. Первое назначение не требует предварительно назначить пользователю роль через этот же API.

### PUT role-binding: замена и access (F2)

PUT задаёт желаемое состояние **соответствующего binding scope**, а не добавляет ещё одну active роль при каждом вызове. Canonical identity scope: для обеих UK roles вместе — `(app_user_id, current organization_id)`; для CONTRACTOR_EMPLOYEE — `(app_user_id, contractor_id)` с `organization_id=NULL`; для RESIDENT — `(app_user_id, RESIDENT)` с shape Data Model §6.2, допускаемый только через own preconfigured scenario access, без создания/смены premises access. Premises не является полем/identity RoleBinding. UK bindings имеют `contractor_id=NULL`; non-UK не получают UK organization binding. В каждом соответствующем scope после успешного PUT максимум одна active binding; разные foreign scopes не объединяются и не редактируются.

- Для UK scope update/replacement меняет существующую canonical binding на запрошенную `UK_EMPLOYEE` или `UK_ADMIN`; смена роли деактивирует все остальные active UK bindings этого же пользователя в `O` **в той же transaction**. Нельзя оставить одновременно active UK_EMPLOYEE и UK_ADMIN в `O`, а затем полагаться на fail-closed auth. При первом назначении создаётся binding, при повторном используется существующая: первая active row в stable PK order, а при отсутствии active — первая inactive row соответствующего scope в том же порядке; остальные строки этого scope остаются inactive. Для resident/contractor scope применяется та же create/update/reactivate/deactivate семантика без изменения foreign scopes. Contractor employee endpoint использует этот же contractor scope и не создаёт второй active binding.
- Omitted `active` означает **`true`**, включая первое назначение и реактивацию. Явное `active=false` сохраняет желаемую binding inactive (при отсутствии создаёт inactive), деактивирует остальные active bindings соответствующего scope и не удаляет AppUser/binding/history. UK deactivation также деактивирует все own UKHouseAccess этого пользователя в `O`; чужие строки неизменны. AppUser.active и current authorization продолжают проверяться отдельно; inactive AppUser не получает LIVE rights от active binding.
- `house_ids` — полный желаемый набор own UKHouseAccess для UK PUT, **не append**. Все IDs проверяются на принадлежность `O`; для active UK binding указанные строки создаются/реактивируются, own строки вне набора деактивируются. Повторы ID не создают дополнительные строки. При `active=false` предоставленный набор всё равно валидируется, но все own UKHouseAccess остаются inactive. Все эффекты binding/access атомарны и полностью отражаются в same-command audit.
- `house_ids=[]` деактивирует все явные own UKHouseAccess: active UK_EMPLOYEE остаётся без доступа к домам; active UK_ADMIN сохраняет computed admin access ко всем **только own** домам по TG-011 / Data Model §6.4. Для RESIDENT и CONTRACTOR_EMPLOYEE требуется `house_ids=[]`; непустой набор — `422`, без effects. Их PUT не меняет UKHouseAccess и не заменяет UK binding: это другой canonical scope, выбранный session binding не подменяется и права не union'ятся.

### Category server-owned metadata (F4)

POST Category сохраняет `config_revision=1`, server transaction timestamps и `updated_by_user_id=effective admin app_user_id`. Каждый успешно committed PATCH Category с новым command увеличивает persisted `config_revision` ровно на `1` от значения, прочитанного под canonical lock, и устанавливает `updated_at` и `updated_by_user_id` текущего effective admin в той же transaction с config/audit/success. Это относится ко всем Category whitelist updates, включая active/default/result изменения и accepted same-value PATCH. Omitted product fields сохраняются; создание/обновление других сущностей не меняет Category metadata. Same-key replay, denied/invalid command и rollback не меняют revision/timestamp/actor. Nullable actor в Data Model допускает предсозданные записи без известного автора; API POST/PATCH всегда пишет authoritative actor, никогда client value или NULL.

`config_revision` — **metadata only**, не CAS correctness gate, не request precondition и не замена row locks. Клиент не задаёт revision/updated actor/timestamps; strict TG-002 requests отвергают эти поля. TG-002 response schemas не расширяются ради metadata.

### Command kernel и audit

Все mutations используют **тот же TG-012 kernel**, `APP_USER` principal effective admin, обязательный `Idempotency-Key`, canonical fingerprint, reservation/wait/replay, current authorization до protected duplicate decision и rollback/finalization. Проверяются requested и stored config contexts при различии. Non-Case command не получает искусственный Case/revision. Handler не реализует локальную reservation, replay cache, повторный policy порядок или CAS.

Каждый successful configuration write обязан записать `ConfigurationChange` **в той же DB transaction**: `config_change_id`, own `organization_id`, `entity_type`, UUID `entity_id`, `action`, nullable `before_data`, non-null JSON `after_data`, authoritative `actor_user_id`, `occurred_at`, FK `command_id` к текущей execution (§33 Data Model). Before — persisted состояние до изменения, прочитанное под locks; after — persisted результат, а не необработанный request. Creation имеет `before_data=null`; update/reactivation/deactivation — реальные before/after, включая active/mapping/requirement изменения. Составные эффекты (Contractor + OrganizationContractor, role binding + UKHouseAccess) должны быть полностью отражены в audit payload/records с одним command_id; не терять side effects и не подменять composite key строкой вместо canonical UUID entity_id. Конкретная representation использует согласованный TG-007 audit surface; несовместимость — blocker, без изменения schema здесь.

Нельзя вернуть successful write без persisted audit. Ошибка mutation/audit insert/kernel finalization откатывает **все** config effects, audit и reservation/success вместе. Same-key authorized replay возвращает stored status/body без повторного config write/audit; accepted same-value mutation не освобождается от обязательного audit. Append-only enforcement TG-007 сохраняется, audit не заменяется логом/outbox/CaseEvent.

### Locking и historical stability

Единый порядок: **principal/key reservation → Case rows, если применимо → Organization → House → Premises → Category → Contractor → OrganizationContractor → actor/access/binding rows по stable PK → child/domain writes**. Несколько строк одной family — stable PK order; duplicate с двумя Case — ascending case_id по TG-012. Config writer без Case не блокирует существующие Case и не берёт Case после config locks; не добавляет bulk rewrite. Блокировать все затронутые dependency/old/new target rows до изменения и удерживать до commit. Для create/bind с отсутствующей child row использовать existing parent scope locks того же protocol и canonical constraints; отсутствие строки не разрешает несериализованную проверку.

Config writer использует `FOR UPDATE` на затронутых mutable rows в общем canonical order; его собственные atomicity, revalidation и concurrent config-write behavior проверяются локально в TG-018. Production TG-014 CreateCase/SelectContractor/SendAssignment используют compatible `FOR SHARE`/эквивалент, но TG-018 не обязан регистрировать их handlers для своего acceptance. Никаких test-only duplicated lifecycle implementations, advisory locks, mutex, второго framework или revision CAS вместо canonical row locks. Если dependent command первый удержал locks, writer ждёт его commit; если deactivation первой committed, последующая команда перечитывает inactive state и не использует запрещённую конфигурацию без частичных effects. Оба commit orders через реальные production handlers проверяет TG-026; final central registration остаётся TG-029.

**OrganizationContractor deactivation vs CreateCase (F3; cross-module acceptance TG-026):** если locked Category имеет non-null default и coherent snapshot требует active Contractor + own OrganizationContractor (Interface §§10, 24.5, 24.9; Data Model §§7.3, 8.2, 29.4), победа CreateCase означает successful создание Case с прежним `default_contractor_snapshot_id`; deactivation ждёт его commit, затем отключает связь, не меняя snapshot/history. Победа deactivation означает, что CreateCase после ожидания и revalidation получает **`422` inactive dependency**: не создаются Case, CaseIteration, initial Attachment/link rows, EVT-001, DemoRun primary bind или successful CommandExecution этого create; reservation откатывается по TG-012. Успешная config deactivation сохраняет свой audit/success. Нельзя обходить отказ, снимая default, записывая NULL вместо configured default, выбирая другого contractor или оставляя частичный Case. Category.default_contractor_id и старые snapshots не переписываются деактивацией связи; повторный create возможен только после разрешённой конфигурации (reactivation либо явный Category default update) и новой проверки. При `default_contractor_id=NULL` эта contractor dependency не требуется. Это semantic outcome существующего lock protocol, без новых locks/framework; полную race проверку выполняет TG-026.

House/Category deactivation запрещает **новые** Case. Category/default/result/access configuration update влияет на новые snapshots; существующие Case сохраняют `category_name_snapshot`, `requires_access_snapshot`, `result_requirement_snapshot`, `default_contractor_snapshot_id`, `house_address_snapshot`, `premises_label_snapshot` и immutable историю. Category deactivation сама по себе не блокирует lifecycle существующего Case (Product Spec §§10.7, 18.4, AC-050 имеют приоритет над общим техническим wording Interface §24.9). SelectContractor/SendAssignment revalidate текущие Contractor/OrganizationContractor и применимые access/bindings; deactivated binding запрещает их использование в будущих selection/send, даже при старом default snapshot. Config не ретаргетит Selection/Assignment, не принимает/отзывает задания и не закрывает Case. Current authorization может измениться немедленно по TG-011, но snapshots/history от этого не мутируют.

## 9. Acceptance criteria

Все endpoint из §7 реализуют только approved surface; UK_ADMIN own-org матрица и current policy соблюдаются на reads, writes и replay. Mutations не допускают tenant selection/чужие mappings. Ровно четыре роли и три result requirements; default не создаёт workflow effects. Каждый успешный write имеет complete before/after audit в общей transaction; audit failure исключает successful mutation. Kernel reused, собственный canonical lock order и config revalidation доказаны; concurrent config writes linearize по committed order. Existing Case snapshots/history стабильны. Production config-command races и дальнейший lifecycle по неактивной Category полностью проверяет TG-026. Implementation завершение TG-018 подтверждается локальным §10, без расширения write scope.

## 10. Required tests

На implementation stage обязательны API tests и **real PostgreSQL** transaction/concurrency suites для собственных config writes, с управляемыми barriers, двумя sessions и проверкой committed rows; sleeps/mock/SQLite не заменяют evidence.
