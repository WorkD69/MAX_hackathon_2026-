Результат будущего исполнения: полный `README.md`, проверочный runbook в `docs/submission/**`, исходник презентации и открывающийся PDF. Все факты о live deployment имеют ссылку на финальное evidence; неустановленные значения не превращаются в заявления.

## 6. README: обязательное содержание

README описывает назначение и конкретную жилищную проблему, приоритетного пользователя, основной путь **Житель → УК → Подрядчик → Житель → УК**, архитектуру реально собранного приложения, четыре рабочих представления (Житель, Сотрудник УК, Администратор УК, Сотрудник подрядчика) и ровно восемь состояний: `Создано`, `Принято УК`, `Передано подрядчику`, `Исполнение`, `Ожидается проверка результата`, `Замечания рассматриваются`, `Доработка`, `Завершено`. Отдельно объясняет, что отправка назначения не означает принятия, а замечание продолжает тот же `case ID`.

README даёт проверенные локальные команды clone/configure/start/stop/restart, one-command Docker/compose startup, no-secret `.env.example` и объяснение необходимых env-переменных, фактические порты и зависимости, MAX Bot/Mini App и HTTPS, модель данных/хранилище и persistence, тестовые роли/данные, автоматизированные проверки и ожидаемые результаты, ограничения и публичный доступ. Имена переменных, порты, пути и команды берутся из финальных артефактов; каждый пример запуска выполняется при проверке, не копируется из предположений.

## 7. Runbook: путь нового проверяющего

В `docs/submission/**` записать последовательность с входными условиями, командами и наблюдаемым результатом каждого шага:

1. Клонировать зафиксированный репозиторий/кандидат и проверить SHA.
2. Создать локальную конфигурацию из no-secret template; показать, какие значения нужны и как получить их вне репозитория, не публикуя рабочие секреты.
3. Одной подтверждённой командой собрать и поднять локальные компоненты; дождаться readiness и сверить `build_sha` там, где он доступен.
4. Открыть работающий Bot и Mini App **через MAX**, пройти старт DemoRun и роли, основной случай, результат, замечание и доработку того же `case ID`; описать повторный прогон без ручного вмешательства разработчика.
5. Выполнить реальные команды automated checks из финального checkout и указать критерии успешного завершения.
6. Остановить и перезапустить локальные сервисы без потери данных; проверить готовность и сохранность случая. Явно отделить восстановление от уничтожения volume/данных.

Прямой URL web-приложения может служить диагностике, но основной экспертный маршрут начинается в MAX. Fresh-reader rehearsal делает человек, не писавший инструкции: с чистого checkout проходит все шаги, фиксирует фактические команды, результат и исправления текста.

## 8. Презентация и технический первый слайд

Исходник и PDF содержат только проверяемые возможности кандидата. Первый слайд — техническая инструкция: рабочий доступ в MAX, репозиторий, полный candidate SHA, публичные app/API URL (или явное объяснение единого адреса), тестовые роли и синтетические данные, краткий demo route. Значения берутся из TG-032/TG-033 и сверяются с `/api/v1/system/info.build_sha`; после TG-035 фиксированный исходный SHA/архив указывается в handoff, а различие с deployed candidate требует явного согласования и повторной проверки gate. Слайд не содержит токенов, паролей, API-ключей и иных рабочих секретов. Если проверке нужен секрет, его канал передачи определяется отдельно вне репозитория; PDF в репозитории его не копирует.

Проверить, что PDF открывается, текст первого слайда читаем, адреса кликабельны/точны, ссылки ведут на существующие цели, а скриншоты и подписи соответствуют candidate SHA. Скриншоты прежнего candidate SHA не используются как доказательство текущего.

## 11. Критерии приёмки и проверки

- `README_SCOPE`: все поля § 6 заполнены фактами final candidate; команды, порты, env и зависимости совпадают с доставленными файлами.
- `RUNBOOK`/`FRESH_READER_TEST`: независимый проверяющий проходит § 7 с чистого checkout, включая MAX, readiness, demo, automated checks и restart/persistence; сохраняет протокол результата.
- `PRESENTATION`/`FIRST_SLIDE`: PDF открывается, первый слайд содержит полный набор § 8, ссылки и файлы существуют.
- `SYNTHETIC_DISCLOSURE`/`NO_UNSUPPORTED_CLAIMS`: соблюдены §§ 5 и 9, различены реальные действия приложения и демонстрационные данные.
- `EVIDENCE_TRACEABILITY`/`SECRET_BOUNDARY`: каждое live/deployment утверждение имеет evidence того же SHA; скан итогового набора и Git diff не находит рабочих секретов.
- `WRITE_SCOPE`: `git diff --name-only` содержит только разрешённые файлы; обязательные submission files из TG-030/031 существуют и проверены, но не переписаны здесь.

Команды будущего исполнителя: `git status --short --branch`, `git rev-parse HEAD`, `git diff --name-only`, команды запуска/проверки из реально доставленных manifests, проверка всех локальных ссылок/внешних URL и наличия файлов, secret scan итоговых материалов и Git diff, открытие PDF и осмотр первого слайда, повторный `git status`. Точные команды и результаты записать в отчёте; нельзя объявлять PASS по одному текстовому осмотру или тестовому MAX adapter.

## 12. Эскалация, передача и Git

`SPEC CONFLICT` при необходимости менять MUST, роли, восемь состояний, инварианты или критерии приёмки: остановиться, передать решение команде; изменение Freeze/Spec возможно только по явному решению с записью в `docs/07_DECISIONS.md`. `INTEGRATION BLOCKER` при отсутствии обязательного TG-033 live evidence или расхождении build/source SHA: вернуть дефект владельцу, получить новый стабильный SHA и повторить затронутые gate. Также остановиться при несовпадении `BASE_SHA`, выходе за file ownership, недоступном MAX/public URL, утечке секрета или сломанном runbook; не подменять факт заглушкой.

Будущий исполнитель передаёт README, runbook, презентацию/PDF, протокол fresh-reader rehearsal и проверок, матрицу утверждение→evidence, список открытых ограничений и точечный cleanup request. После проверок делает commit и push своей ветки существующей человеческой Git identity, возвращает полный commit SHA и статус push. Интеграцию в стабильный `main` выполняет отдельный Integration Agent; TG-035 получает проверенный checkpoint. Текущий проход передаёт только этот контракт и его self-check/commit SHA.
