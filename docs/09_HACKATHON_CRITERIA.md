# Подтверждённые требования хакатона

Здесь приведены только требования официального кейса «Умный город.pdf» и фактические уточнения организаторов на официальной трансляции 17.09.2026. Рекомендации и примеры выступавших не становятся обязательными требованиями. Указанные страницы относятся к официальному кейсу; отметка `W17` — к официальной трансляции по документу `MAX_Hackathon_2026_Track_Webinar_Evidence_Product_Delta_Review_2026-09-17.md`.

## 1. Admission / обязательные условия

- Решение должно относиться к управлению многоквартирным домом или жилищной проблеме, иметь обоснованную актуальность и использовать MAX как среду реализации или взаимодействия. Основной сценарий должен быть проверяемым в MAX. **Источник:** кейс, с. 6–7.
- Нулевой балл без дальнейшей оценки получает решение вне темы/без использования MAX, решение, у которого бот или Mini App в MAX не запускается либо основной сценарий невозможно проверить, а также решение без презентации. **Источник:** кейс, с. 11; подтверждение `W17 00:07:33–00:08:15`.
- Для онлайн-этапа требуется определить приоритетного пользователя и конкретную проблему, показать основной путь, MVP, ожидаемый проверяемый эффект и потенциал масштабирования. **Источник:** кейс, с. 6.
- Запрещены закрытые библиотеки, частные API и чужой код без разрешения на свободное распространение и использование. **Источник:** кейс, с. 7.
- Оценка каждого критерия — от 0 до 3 баллов. **Источник:** кейс, с. 11.

## 2. Product evaluation

Продуктовая оценка составляет **40%** балла онлайн-этапа. Внутри неё: потенциал масштабирования — **35%**, пользовательская ценность — **25%**, UX/UI и удобство — **20%**, обоснованность и целостность — **15%**, качество презентации — **5%**. Оцениваются конкретный пользователь и результат, доказательства или аргументированные допущения, понятный полный путь, условия адаптации и реалистичность решения. **Источник:** кейс, с. 12.

Для финала техническая оценка продукта составляет **40%**, защита — **60%**. В защите оцениваются ценность и соответствие задаче (25%), масштабирование (25%), качество MVP и пользовательского опыта (20%), сценарий запуска (15%), качество защиты (10%), командное владение решением (5%). Платформенный бонус онлайн-этапа в итог финала не переносится. **Источник:** кейс, с. 14.

## 3. Technical evaluation

Техническая оценка составляет **60%** балла онлайн-этапа. Внутри неё: работоспособность и полнота основных функций — **30%**, интеграция и обмен данными — **20%**, стабильность и обработка ошибок — **10%**, техническая реализация и архитектура — **20%**, безопасность, зависимости и данные — **10%**, техническая документация и комплектность — **10%**. Основной сценарий должен проходить до результата и повторяться; ошибочные действия обрабатываются с возможностью продолжить работу. **Источник:** кейс, с. 13.

Дополнительная возможность MAX может дать **+0,15 балла** только целиком, если она создаёт ценность, работает в основном сценарии от начала до результата и описана в материалах. Собственный API или количество функций сами по себе бонуса не дают. **Источник:** кейс, с. 13.

## 4. Submission requirements

- Передать работающий доступ к боту или Mini App в MAX, чтобы эксперты прошли основной сценарий. Решение должно оставаться доступным во время проверки. **Источник:** кейс, с. 9; уточнение `W17 ~00:05:50–00:07:25`.
- Передать зафиксированную версию исходного кода: Git-репозиторий с commit hash либо архив с контрольной суммой. После дедлайна переданная версия не изменяется; финалисты смогут вносить изменения после объявления результатов онлайн-этапа. **Источник:** кейс, с. 7, 9; `W17 ~00:03:10–00:05:30`.
- Передать README с назначением, основным сценарием, составом и архитектурой, одной командой запуска локальных компонентов через Docker, параметрами и переменными окружения, портами, зависимостями, интеграциями, работой с данными и тестовыми данными, шагами проверки, ожидаемым поведением, ограничениями, остановкой и повторным запуском. Эти требования относятся к **сдаче работающего MVP**, а не к текущему README до реализации. **Источник:** кейс, с. 9.
- Передать файл зависимостей с версиями и презентацию в PDF. Первый слайд презентации — технические сведения для проверки: доступ в MAX, репозиторий и commit hash, адрес API при его наличии, тестовые логины и пароли, рабочие токены и API-ключи, если они необходимы для запуска и проверки, другие необходимые значения окружения, краткий маршрут проверки. Этот слайд не оценивается как продуктовая презентация. Рабочие секреты при этом запрещено размещать в репозитории. **Источник:** кейс, с. 7, 9–10.
- Онлайн-этап завершается **30.09.2026 в 12:00**; финалисты объявляются **14.10.2026**; очный финал в Казани — **29.10.2026**. Онлайн-защиты нет. **Источник:** уточнение организатора `W17 ~00:03:10–00:05:30`, `00:30:24–00:31:47`.

## 5. MAX requirements

- MVP создаётся как бот либо бот с подключённым Mini App, с использованием выданного организаторами токена. Mini App подключается к боту и не выступает изолированным сервисом. **Источник:** кейс, с. 6–7, 15; уточнение `W17 ~00:35:40–00:36:12`.
- MAX — реальная среда основного проверяемого пути. Если используется Mini App, подключение к MAX требует HTTPS. После создания ник бота изменить нельзя. **Источник:** кейс, с. 7, 15.
- Реализовать только бот допустимо; отсутствие Mini App само по себе не снижает оценку. Это уточнение правил хакатона, а не изменение утверждённого объёма данного продукта. **Источник:** `W17 00:41:05–00:41:13`; Product Freeze отдельно требует Bot + Mini App.
- Соблюдать актуальные правила MAX, законодательство РФ и опубликованные правила хакатона. **Источник:** кейс, с. 7.

## 6. Mobile / web requirements

Можно разрабатывать с использованием мобильной или веб-версии MAX, но функциональность решения должна быть доступна пользователям **в обеих версиях**. **Источник:** кейс, с. 7.

## 7. Synthetic / test data rules

- Тестовые, подготовленные или смоделированные данные допустимы вместо реального подключения к внешней системе, если это **явно указано в материалах**. Их происхождение и роль в демонстрации должны быть понятны. **Источник:** кейс, с. 7–8; `W17 ~00:40:19–00:40:50`.
- Организатор подтвердил достаточность вымышленных/синтетических данных для демонстрации; это не освобождает от требований к безопасности и персональным данным. **Источник:** `W17 01:46:24–01:48:30`.
- При использовании официальных данных нужно проверять первоисточник, актуальность и применимость к территории, периоду и пользователю; отделять исходные факты от расчётов, рекомендаций и модельных данных. **Источник:** кейс, с. 18.
- Рабочие токены, пароли, API-ключи и иные секреты нельзя размещать в репозитории. **Источник:** кейс, с. 7, 13.

## 8. Docker / README requirements

- К сдаче решение должно воспроизводимо запускаться через Docker. Для локально запускаемых компонентов в репозитории требуются Dockerfile, `compose.yaml` или `docker-compose.yml`, `.dockerignore` и `.env.example` без рабочих секретов. Один запуск должен поднимать все необходимые локальные компоненты. **Источник:** кейс, с. 9.
- Сборка Docker должна занимать не более **5 минут** без времени первоначальной загрузки базовых образов; конфигурация содержит только необходимые компоненты. Готовый образ не заменяет файлы для сборки из переданного исходного кода. Контейнеризация не заменяет работающий доступ к продукту в MAX. **Источник:** кейс, с. 9.
- Требуемое содержание README приведено в разделе 4. На текущей стадии нет кода и команд запуска; эти требования входят в этап подготовки сдачи. **Источник:** кейс, с. 9.

## 9. Own API requirements — только если API будет реализован

Собственный API **не обязателен** и сам по себе не даёт дополнительных баллов. Если он есть, для сдачи необходимы: проверяемый HTTPS-адрес на период проверки; OpenAPI 3.0 или 3.1 (`openapi.yaml`/`openapi.json`); тестовые учётные записи по нужным ролям; тестовые данные; `DATA-API.yaml` с версией конфигурации, идентификатором решения, базовым адресом, перечнем обязательных проверок, методом и путём, параметрами запроса, ролью, ожидаемыми кодами и форматом ответа. **Источник:** кейс, с. 7, 10, 13.

## 10. Что нельзя выдавать за реальную интеграцию

Подготовленные, тестовые и смоделированные данные нельзя представлять как данные действующей внешней системы; отсутствие реального подключения нужно явно раскрыть. Для модельной интеграции следует указать, что понадобится для реальной после MVP. Нельзя заявлять работающую внешнюю интеграцию или официальную регистрацию обращения, если они не реализованы и не проверяются. Реальные внешние сервисы, если используются, должны быть описаны вместе с условиями доступности при проверке. **Источник:** кейс, с. 7, 9, 13, 18; разграничение демонстрационных и реальных возможностей — [Product Freeze, разделы 18–20](01_PRODUCT_FREEZE.md).
