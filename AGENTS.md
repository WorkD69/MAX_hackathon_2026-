# Правила работы в репозитории

## Перед любой задачей

- Выполнить `git status` и `git rev-parse HEAD`; для первой задачи в пустом репозитории зафиксировать отсутствие `HEAD`.
- Читать только документы, необходимые для текущей задачи. Текущая стадия и маршруты: [состояние проекта](docs/08_PROJECT_STATE.md), [передача оркестратору](docs/ORCHESTRATOR_HANDOFF.md).
- Не обращаться к прежним репозиториям и прежним продуктовым исследованиям.

## Приоритет и границы

- Иерархия: официальные требования → официальные уточнения → [Product Freeze](docs/01_PRODUCT_FREEZE.md) → [Product Spec](docs/02_PRODUCT_SPEC.md) → будущая техническая спецификация → код.
- Для продуктовой логики нормативны `docs/01_PRODUCT_FREEZE.md` и `docs/02_PRODUCT_SPEC.md`; техническая архитектура не меняет продукт.
- Самостоятельно не менять scope, MUST, восемь состояний, роли, основной сценарий, инварианты и критерии приёмки ради реализации.
- Если код требует изменения продуктового правила: **STOP; сообщить `SPEC CONFLICT`**. Не писать обходное решение. Изменение Freeze или Spec требует явного решения команды и записи в [журнал решений](docs/07_DECISIONS.md).

## Задачи и интеграция

- Начиная с Wave 2, необходимость и порядок оформления Task Contract определяются risk-class workflow в [BACKLOG](tasks/BACKLOG.md). Если контракт нужен, использовать [шаблон](tasks/TASK_TEMPLATE.md); для DELIVERY-задачи при однозначных canonical docs отдельный контракт не обязателен.
- Агент изменяет только разрешённые файлы. Если задаче назначен `BASE_SHA`, перед работой сверяет его с `git rev-parse HEAD`.
- После работы выполнить проверки, показать результат, сделать commit и push, вернуть commit SHA.
- После каждой параллельной волны отдельный Integration Agent объединяет изменения и создаёт новый стабильный `main`. Параллелить независимые задачи; одно решение принимает один ответственный.

## Git и язык

- Использовать существующую человеческую Git identity. Не добавлять AI author, AI co-author или подписи `Generated-by-AI`.
- Документация ведётся на русском; английский допускается для официальных и устойчивых технических терминов.
